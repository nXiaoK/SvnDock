# SvnDock Finder Sync Extension

This directory contains the Finder integration source. It supports
an unlimited set of registered working-copy roots, status badges, contextual
menus, and a durable hand-off to the main SvnDock application.

## Security boundary

The extension is intentionally a thin UI/cache process:

- It never launches `svn`, `Process`, a shell, or a network request.
- It never reads or writes `.svn/wc.db` and never handles credentials.
- It reads two bounded JSON snapshots from the shared App Group container.
- It writes immutable command requests to an append-only inbox, then makes a
  best-effort `svndock://finder-command?...` wake-up call.
- It never puts selected paths, credentials, or repository URLs in the custom
  URL. If wake-up fails, the JSON request remains queued for the next app run.
- The main app/agent must treat queue files as untrusted input, revalidate the
  root and paths, prompt for destructive operations, and serialize mutations
  per working copy.

## Xcode target integration required

`project.yml` already defines a **Finder Sync Extension** target. When wiring
the target manually instead, add these four Swift files to that extension only:

- `SharedModels.swift`
- `SharedContainer.swift`
- `FinderCommandDispatcher.swift`
- `FinderSync.swift`

Set its Info plist to `FinderExtension/Info.plist` and its entitlements to
`FinderExtension/FinderExtension.entitlements` (or configure the same App Group
in Signing & Capabilities).

Before signing, configure identifiers once in the root `project.yml`:

1. Set `SVNDOCK_BUNDLE_ID_PREFIX` to a prefix owned by your team.
2. Set `SVNDOCK_APP_GROUP_IDENTIFIER` to the App Group enabled on both the main
   app and extension. The generated Info plist and entitlements expand this
   same value automatically.
3. Keep the `svndock` URL scheme unchanged; it is currently a fixed internal
   protocol shared with the main application's router.
4. Embed the extension in the main app's `PlugIns` build phase and sign both
   products with the same team.

Those instructions assume the project is generated with XcodeGen. If the app
and extension targets are created manually, `project.yml` is not loaded: define
the two custom settings in Xcode or an xcconfig and give the extension the
derived bundle identifier there.

Debug SwiftPM builds retain the development App Group fallback because their
Info plist is not processed by Xcode. Release extension storage rejects a
missing, empty, or unexpanded App Group value rather than silently using the
development identifier.

The main app should post this distributed notification after atomically
replacing either snapshot:

```swift
DistributedNotificationCenter.default().post(
    name: Notification.Name("com.svndock.shared-state-changed"),
    object: nil,
    userInfo: nil
)
```

The extension also reloads snapshots whenever Finder requests a menu, so a
missed notification is recoverable.

## Shared container contract (schema version 1)

All paths below are relative to the App Group container:

```text
Library/Application Support/SvnDock/
├── registered-roots.json
├── badge-snapshot.json
└── command-queue/
    └── <lowercase-uuid>.json
```

`registered-roots.json` is written atomically by the main app:

```json
{
  "schemaVersion": 1,
  "roots": [
    {
      "id": "4A44EAE7-C452-4D83-807F-42B0D19BF621",
      "path": "/Users/me/Projects/example",
      "displayName": "Example",
      "enabled": true
    }
  ]
}
```

`badge-snapshot.json` is a full replacement generated by the trusted main
app/agent. Include aggregate entries for roots/directories if those folders
should display a badge:

```json
{
  "schemaVersion": 1,
  "generatedAt": "2026-09-04T08:00:00.000Z",
  "entries": {
    "/Users/me/Projects/example": "modified",
    "/Users/me/Projects/example/File.swift": "conflicted"
  }
}
```

Badge values are `modified`, `added`, `deleted`, `conflicted`, `unversioned`,
`missing`, `replaced`, `ignored`, and `clean`. `ignored` and `clean` intentionally
clear the badge.

The extension creates a command request like this:

```json
{
  "createdAt": "2026-09-04T08:00:01.123Z",
  "id": "0AA588F2-C083-4CDD-94E2-0700AD628732",
  "kind": "diff",
  "paths": ["/Users/me/Projects/example/File.swift"],
  "schemaVersion": 1,
  "source": "finder-extension",
  "workingCopyRoot": "/Users/me/Projects/example"
}
```

Supported `kind` values are `openApp`, `refresh`, `update`, `commit`, `diff`, `add`,
`revert`, `cleanup`, `log`, `resolve`, `copyRepositoryURL`, `ignoreName`, and
`ignoreExtension`.

## Runtime behavior and limitations

- Finder allows multiple monitored `directoryURLs`; the extension supplies all
  enabled roots from the registry and chooses the deepest root for nested copies.
- A command is refused when selected items cross working-copy boundaries.
- The contextual menu uses cached status only for its summary label. Common
  actions remain visible when the cache is stale; selecting **Refresh Status**
  opens the main app for an authoritative read and badge update. The main app
  also owns operation-specific validation and confirmation UI.
- A single versioned item exposes history; an exact conflict badge exposes the
  resolve workflow; and an exact unversioned badge exposes name/extension ignore
  rules. The app rechecks all three against fresh SVN state before execution.
- Users must enable the Finder extension in macOS System Settings. Finder badge
  ownership can conflict with iCloud Drive, Dropbox, and other Finder extensions.
- Finder decides menu placement and may coalesce or delay badge callbacks.
